### 1: Turning Line Equations Into Triangle Vertices

- A triangle here isn't drawn from 3 points directly — it's derived from 3 line equations, where each pair of lines intersects at one vertex.
- Parsing user text (y=2x+3, x=4) needs a distinction between sloped lines (y=mx+c) and vertical lines (x=k), since a vertical line has no defined slope and would break the normal formula.
- Finding where two lines meet is just solving two equations for the same (x,y): for two sloped lines, setting m1x+c1 = m2x+c2 and solving for x, then plugging back in for y.
- Parallel lines (same slope, or both vertical) never intersect — the program has to detect this case explicitly and show an error instead of dividing by zero or drawing nonsense.
- Regex (Pattern/Matcher) is what extracts the numbers out of a typed string like "y=-2x+3" — breaking it into the slope part and the constant part before doing any math on it.

### 2: Canvas + GraphicsContext — The Drawing Toolkit

- A Canvas is a blank drawing surface; GraphicsContext is the object that actually issues drawing commands onto it (fillOval, strokeLine, fillRect, fillText).
- fillOval/strokeOval need a bounding box, not a center point — which is why drawing a circle at a "center" always means subtracting the radius first to get the top-left corner the method expects.
- Unlike Swing's paintComponent() model, drawing on a Canvas is direct and immediate — calling gc.fillOval(...) draws right away, rather than waiting for a repaint cycle.
- Draw order matters: shapes drawn later appear on top of shapes drawn earlier — this is why, in the tree program, edges are drawn before the node circles, so the lines don't cut across the node labels.


### 3: Right-Click to Draw a Circle, and Connect It to the Last One

- Every click on the canvas fires the same event — we just check event.getButton() == MouseButton.SECONDARY to know it was a right-click, not a left-click. Left-clicks are simply ignored.
- Whenever a right-click happens, we draw a circle at that click's (x, y) position.
- The program keeps a list that remembers every circle's position so far, in the order they were clicked.
- Before drawing the new circle, we check: was there an earlier circle? If yes, we draw a line (arrow) from that last circle to the new one, so each new click connects to the one right before it.
- Simple way to think about it: click 1 → just a circle. Click 2 → circle + arrow from circle 1. Click 3 → circle + arrow from circle 2. And so on.

### 4: How the Arrow Actually Gets Drawn

- JavaFX doesn't have a built-in "draw arrow" command — so an arrow is really just 3 lines: one long line connecting the two circles, plus two short lines at the tip forming a "V" (the arrowhead).
- To draw those 3 lines correctly, we first need to know the direction from the old circle to the new one — this direction is calculated using Math.atan2(), which just gives us the angle of the straight line between the two points.
- Using that angle, the two short arrowhead lines are drawn slightly tilted (25 degrees left and 25 degrees right) from the main line, right at the new circle's edge — that's what makes it look like an arrow tip instead of a plain line.
- We also shorten the line slightly on both ends, so it starts and ends at the edge of each circle instead of going straight through the middle of them — otherwise the line would be hidden behind the circles.

         

### 5: Drawing a Binary Tree Recursively

- The tree is just nodes with a value and optional left/right children — no special drawing logic lives in the node class itself, all of that is handled separately during drawing.
- The key layout idea: each node is drawn at some (x, y), and its children are placed one level down and offset left/right by an xOffset — but that offset is halved on every recursive call.
- Halving the offset each level is what prevents deeper nodes from overlapping — the root's two children are far apart, but by 3-4 levels down the spacing has shrunk enough to still fit visually without collisions.
- Recursion here mirrors the tree's own structure: drawNode(node) calls drawNode(node.left) and drawNode(node.right), stopping naturally when a child is null — no separate loop or counter needed to know when to stop.

            drawNode(x, y, xOffset)
                     |
          +----------+----------+
          |                     |
      Left Child            Right Child
          |                     |
    Line + Recurse         Line + Recurse
    (xOffset / 2)          (xOffset / 2)
          |                     |
          +----------+----------+
                      |
              Draw Circle + Label

**Reflections:**

- **Line equations → triangle:** Realized the triangle isn't really "drawn" directly — it emerges as a side effect of solving 3 pairs of equations for their intersection points.
- **Canvas drawing:** The canvas doesn't remember anything by itself — once a shape is drawn, that's it, it's just pixels. So if the program needs to "remember" where something was drawn, it has to store that in a variable, not rely on the canvas.
- **Right-click tracking:** Same idea here — the only reason a new circle can connect to the last one is because the program keeps a list of all previous clicks. Without that list, every click would be its own separate circle with no connection.
- **Arrow math:** Didn't expect an arrowhead to just be two small angled lines — using atan2 to get the direction was the main trick that made the rest of it simple.
- **Recursive tree drawing:** Halving the offset each level made sense once I saw it drawn out — and it's basically doing the same kind of thing as the arrow angle in Topic 4: taking some math (an angle, a tree depth) and turning it into an actual screen position, instead of typing fixed numbers by hand.


**Q&A Discussed:**

- Q: Why does the triangle program need to check for parallel lines specifically?
  A: Two parallel lines never intersect, so the normal intersection formula would divide by zero (equal slopes) — this has to be caught before doing the math, not after.

- Q: Why does drawing a circle need the radius subtracted from the center coordinates?
  A: fillOval expects a bounding box's top-left corner, not a center — subtracting the radius from both x and y converts a center point into that expected corner.

- Q: How does the program know where to draw a line back to the "previous" circle?
  A: It keeps a running list of every circle's center as it's added — the last item in that list is always the "previous" one for the next click.

- Q: Why is atan2 used instead of a plain arctangent for the arrow's angle?
  A: atan2 correctly handles all four directions (including when dx or dy is negative), while a plain arctangent alone can't distinguish those cases properly.

- Q: Why does halving the offset each level prevent nodes from overlapping?
  A: Each level splits the horizontal space in half again, so no matter how deep the tree gets, siblings at that level are still spaced apart proportionally to how much room is left.
